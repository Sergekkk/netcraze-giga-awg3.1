# Архитектура интеграции AmneziaWG v3 в Keenetic OS (NDMS)

В данном документе описано архитектурное устройство решения, логика разделения конфигураций, жизненный цикл интерфейсов и взаимодействие с подсистемой маршрутизации NDMS.

---

## 1. Общая схема компонентов

```
+-------------------------------------------------------------------------+
|                              KeeneticOS                                 |
|                                                                         |
|  +---------------------------+       +-------------------------------+  |
|  |     NDMS CLI / ndmc       | <---> |   Keenetic Web UI / Routing   |  |
|  | (Объекты OpkgTun0..N)     |       |    (Политики, приоритеты)     |  |
|  +---------------------------+       +-------------------------------+  |
|               ^                                      ^                  |
|               | (ndmc команды настройки)             |                  |
|  +------------+--------------------------------------+---------------+  |
|  |                                                                   |  |
|  |  Entware /opt Среда:                                              |  |
|  |                                                                   |  |
|  |  +-------------------------------------------------------------+  |  |
|  |  |                   /opt/etc/init.d/S99awg3                   |  |  |
|  |  |  (Единый сервис: insmod, проверка зависимостей,             |  |  |
|  |  |   управление индексами, запуск и остановка туннелей)        |  |  |
```

## 2. Ключевая концепция: Двухуровневый сетевой стек

В KeeneticOS сетевые интерфейсы управляются через две сущности:
1. **Ядро Linux**: сетевые интерфейсы драйвера (`opkgtun0`, `opkgtun1` с типом `DEVTYPE=amneziawg`).
2. **NDMS (Keenetic Network Operating System)**: высокоуровневые объекты интерфейсов (`OpkgTun0`, `OpkgTun1`), которые отображаются в веб-интерфейсе роутера, участвуют в политиках маршрутизации Policy-Based Routing (PBR), многошлюзовой переадресации (Multi-WAN) и DNS-резолвинге.

### Почему стандартный `awg-quick` / `wg-quick` не подходит напрямую?
* `wg-quick` работает только на уровне Linux и пытается самостоятельно переписать таблицу маршрутизации (`ip route`, `iptables`), что ломает нативную маршрутизацию Keenetic и не интегрирует туннель в веб-интерфейс.
* Наше решение связывает Linux-интерфейс ядра `opkgtunN` с управляющим объектом NDMS `OpkgTunN`.

## 3. Последовательность запуска туннеля в `S99awg3`

Вся логика управления туннелями сосредоточена в сервисе `/opt/etc/init.d/S99awg3`:

1. **Проверка требований:** проверяется наличие модуля `amneziawg.ko`, утилит `awg`, `awg3-split-config`, `ip`, `ndmc`.
2. **Загрузка модуля:** проверка `/proc/modules` и загрузка `/opt/lib/modules/amneziawg.ko` через `insmod`.
3. **Очистка старых интерфейсов:** удаление ранее созданных интерфейсов `opkgtunN` из ядра Linux.
4. **Выделение индекса:** определение постоянного индекса интерфейса (`0..99`) для каждого `.conf` файла с сохранением в `managed.tsv`.
5. **Создание объекта NDMS:** вызов `ndmc -c "interface OpkgTunN"` и назначение описания по имени файла (`description <ИмяФайла>`).
6. **Создание Linux-устройства:** создание сетевого устройства `ip link add opkgtunN type amneziawg`.
7. **Разделение конфигурации:** запуск `/opt/bin/awg3-split-config <config.conf> opkgtunN OpkgTunN`.
8. **Применение параметров AWG:** передача ключей и параметров обфускации (`Jc`, `Jmin`, `Jmax`, `S1`, `S2`, `H1`-`H4`) в ядро через `/opt/bin/awg setconf opkgtunN /opt/etc/awg3/conf/parsed/opkgtunN.awg.conf`.
9. **Применение настроек NDMS:** выполнение скрипта `/opt/etc/awg3/conf/parsed/opkgtunN.ndms.sh` (IP-адрес, MTU, DNS, adjust-mss, включение интерфейса).
10. **Поднятие линка:** `ip link set opkgtunN up`.
11. **Ожидание готовности:** цикл проверки до 30 секунд готовности Linux (`LOWER_UP`) и статуса NDMS (`link: up`).
12. **Сохранение состояния:** атомарное обновление `/opt/etc/awg3/managed.tsv` и сохранение конфигурации NDMS (`system configuration save`).

## 4. Разделение конфигурации (`awg3-split-config`)

Пользовательский файл `.conf` разделяется на два независимых артефакта в папке `/opt/etc/awg3/conf/parsed/`:

1. **`opkgtunN.awg.conf`** — скармливается утилите `awg setconf`:
   - Секция `[Interface]`: `PrivateKey`, а также параметры обфускации: `Jc`, `Jmin`, `Jmax`, `S1`, `S2`, `S3`, `S4`, `H1`, `H2`, `H3`, `H4`, `HeaderProtectionKey`, `ContentPaddingAddition`, `RekeyAfterTime`, `RekeyTimeout`, `RejectAfterTime`, `KeepaliveTimeout`, `MaxHandshakeAttempts`, `RandomTrailers`, `DisableCookies`.
   - Секция `[Peer]`: `PublicKey`, `PresharedKey`, `Endpoint`, `AllowedIPs`, `PersistentKeepalive`.

2. **`opkgtunN.ndms.sh`** — скрипт команд для CLI роутера:
   - `ndmc -c "interface OpkgTunN ip address <IP> <MASK>"`
   - `ndmc -c "interface OpkgTunN ip mtu <MTU>"`
   - `ndmc -c "interface OpkgTunN ip name-server <DNS> \"\" on OpkgTunN"`
   - `ndmc -c "interface OpkgTunN ip global auto"`
   - `ndmc -c "interface OpkgTunN ip tcp adjust-mss pmtu"`
   - `ndmc -c "interface OpkgTunN up"`

## 5. Устойчивое управление индексами (`managed.tsv`)

Чтобы интерфейс туннеля не менял свой номер (`OpkgTun0` -> `OpkgTun1`) при перезагрузках и добавлении новых конфигов, сервис ведет учет в файле `/opt/etc/awg3/managed.tsv`:
```tsv
/opt/etc/awg3/conf/vpn1.conf    0   OpkgTun0
/opt/etc/awg3/conf/vpn2.conf    1   OpkgTun1
```
Это гарантирует, что правила маршрутизации и политики в KeeneticOS не "отвяжутся" от интерфейса при изменении порядка файлов.
